# 新业务页面接入指南

适用对象：业务项目负责人、运维人员，以及替他们修改项目的 AI。本文按当前仓库实现编写；[可直接复制的 AI 任务模板](ai-app-integration-prompt.md)可转给其他人使用。

**职责边界：门户只做集成，不修改子应用源码、UI、业务逻辑、权限实现或数据规则；也不改写构建产物或向 iframe 注入内容。历史改动保留，今后严格分开。详见[集成边界](integration-boundary.md)。**

**接入顺序：只读确认原项目 → 核对现有子路径与嵌入能力 → 配置门户侧映射 → 注册菜单 → 验收。** 注册表只创建入口，不会自动复制文件、启动后端、配置代理或授予权限。

## 路径基准（先统一）

本文提到的文件系统路径以门户根目录为基准。先定位包含 `package.json`、`portal/`、`deploy/` 的目录，令其为当前工作目录；原业务项目使用经核实的相对位置，例如 `../业务项目/`。Markdown 文档链接仍按所在文档的位置解析，业务公共 URL 仍使用 `/capacity/` 这类根相对地址，不要与磁盘路径混淆。

- 默认 SOP 项目候选位置为 `../PythonProject/计划看板`；不同机器先查明原项目再填写，不能为了满足示例而移动源码或创建副本。
- `integration/sop.example.json` 使用相对路径；复制到 `config.local/sop.json` 后仍按门户根目录解析，而非 `config.local/`。
- CLI 示例从门户根目录执行。其他项目按自身工具规则核对解析基准，不假定所有配置都按配置文件目录解析。
- 某些接口确实要求绝对路径：SOP 构建器的 `--destination`、IIS `DeploymentRoot`、SOP 服务器数据/规则路径等。保留现有校验，通过 `Resolve-Path`、`Join-Path`、`GetFullPath` 从当前环境生成；不直接填 `../` 去绕过要求，也不把某台机器的盘符写进接入指南。

## 1. 先确认接入的是什么

| 类型 | 如何识别 | 接入方式 |
|---|---|---|
| 单 HTML 报表 | 浏览器打开即可使用，资源可能已内联 | 导入原项目生成的发布 HTML |
| 多文件静态站点 | 发布目录包含 HTML、JS、CSS、图片等；无运行时后端 | 使用完整构建产物，按应用子路径发布 |
| 动态业务应用 | 页面依赖 Python/Node 等服务、API、数据库或 WebSocket | 运行独立服务，以同源子路径代理接入 |

修改前检查原项目的说明、AGENTS.md、Git 状态、启动/构建命令和真实数据路径。不要根据旧文档中的示例路径直接打补丁。

为应用记录以下信息；能从现有项目查到的先核实，不重复向用户索要：

| 项目 | 需要记录的内容 |
|---|---|
| 身份 | 中文名称、用途、唯一 ID、归属分组、业务负责人 |
| 唯一源码 | 实际原项目目录/仓库、当前版本、构建命令 |
| 页面与服务 | 静态发布目录，或启动命令、回环端口、健康检查路径 |
| 公共路径 | 例如 `/capacity/`；动态服务保留还是剥离此前缀 |
| 数据 | 原始文件、数据库、上传目录、导出目录、规则文件的真实位置 |
| 使用范围 | 部门内部成员使用相同业务功能；核实部门入口与可信操作人记录，不另设只读/可写角色或写入域组 |
| 验收环境 | 本地预览地址；最终内网域名/端口可暂留参数，不阻塞可做的本地工作 |

原项目继续拥有业务源码和数据，门户只维护接入及通用部署逻辑。允许把原项目**构建产物**放入忽略的发布目录，不在门户复制并继续修改第二套业务源码。不要把数据库、原始 Excel、日志、密钥或整个项目目录复制到可下载的静态目录。

在默认相对布局下，SOP 的唯一源码为门户根目录的 `../PythonProject/计划看板`；不可恢复门户中的 SOP 源码副本。新应用也采用同样的源码归属原则。

## 2. 先定好四个名称

以一个尚未存在的“产能分析”应用为例：

| 用途 | 示例 | 由谁维护 |
|---|---|---|
| 应用 ID | `capacity` | 门户注册表 |
| 门户路由 | `/#/app/capacity` | 门户由 ID 自动生成 |
| 业务公共地址 | `/capacity/` | 静态挂载或反向代理 |
| 静态产物目录 | `apps/capacity/index.html` | 从原项目构建产物导入，仅静态应用使用 |

这些是不同概念：`/#/app/capacity` 显示门户外壳，`/capacity/` 才是 iframe 实际加载的页面。动态应用不必有 `apps/capacity` 文件夹。

建议统一采用同一个小写 ID，字母开头，只含小写字母、数字和连字符；静态部署名称最长 40 个字符。避免占用门户的 `assets`、`config`、`css`、`js`、`api`、`data`、`logs`、`services`、`deploy`、`scripts`、`tests` 等路径。`home` 是保留应用 ID，`all` 是保留分组 ID。

现有“库存分析、销量预测、线索分析”已登记为 pending；接入这些项目时更新原条目，不再新增同名应用。

## 3. 核对原业务页面的现有接入能力

本节是兼容性检查清单，不是修改子应用的授权。使用已有配置和构建参数；如果原项目不支持某项要求，记录问题及需要原项目处理的事项，本门户任务保持其原样，不打补丁。

### 子路径、资源与路由

- 门户部署于站点根目录。应用地址必须与门户**同协议、同主机、同端口**，并以应用子路径隔离。
- 页面资源使用相对路径或带应用前缀的路径。例如从 `/capacity/` 加载 `./assets/app.js` 或 `/capacity/assets/app.js`；API 使用 `/capacity/api/...`。
- 检查代码中的 `/api/`、`/static/`、`/assets/`、重定向、表单、下载 URL、Cookie Path、WebSocket 地址，避免落到门户根路径。
- 如有 SPA，按原项目使用的框架版本配置构建公共路径和路由 base。history 回退仅配置在业务应用内；门户不添加全站 fallback 来掩盖 404。
- 应用刷新、直接访问深层路由、从门户切换应用后再进入，都要保留正确前缀。

### iframe 与界面

业务页面必须允许同源 iframe：检查最终响应的 `X-Frame-Options` 和 CSP `frame-ancestors`。通常采用 SAMEORIGIN 与 `'self'`；若原项目禁止嵌入，记录为接入阻塞；不得在门户任务中修改原应用或剥除其响应头。由另行授权的子应用任务决定是否支持嵌入。

门户自身的新页面或组件遵循[设计基准](../design-system/planning-portal/MASTER.md)；子应用 UI 不纳入门户主题改造。门户保留浅色柔彩风格、双色折带 P、约 64px 的单行顶栏；不要重新添加侧边栏、重复应用标题、正常态应用操作条、版本/时间页脚。业务页面中的筛选、维护、导入导出等必要操作不属于这些冗余外壳。

独立应用的样式由其独立任务维护。本门户任务不改其源码、样式、页脚、提示栏或图标，也不操作 iframe DOM、注入 CSS/JavaScript、裁剪内容或替换代理响应正文。若原项目已有内嵌模式，可按其现有接口启用；若没有，只记录需求，不能擅自新增。展示模式不能作为访问授权依据。

## 4. 静态页面怎么接

### 4.1 准备发布产物

使用原项目已有构建命令或负责人提供的发布版本，不修改其源码或产物内容，将完整发布产物导入 `apps/<id>/`：

```text
统一门户/
  portal/                 # 门户外壳，不放业务源码
  apps/
    capacity/
      index.html
      assets/
        app.js
        app.css
```

多文件应用保留目录关系；只复制 index.html 往往会丢资源。若产物有 PDF、CSV、WASM 等文件，检查预览器的 MIME 白名单及 IIS 映射是否支持所需扩展；不能为此开放原始数据目录。更新已有发布目录前先备份，并防止旧版残留资源混入；不要删除原项目或业务数据。

`scripts/Import-OrderIQ.ps1` **只适用于 OrderIQ**，会更新 orderiq 注册状态，不是新应用的通用导入器。其他应用按自己的产物结构导入，并记录源版本和构建方法。

### 4.2 增加本地预览映射

当前 `scripts/dev-server.mjs` 的 `STATIC_APPS` 只有 orderiq 和 inventory。新增 capacity 时，在保留现有项的基础上加入：

```js
export const STATIC_APPS = Object.freeze({
  orderiq: 'orderiq',
  inventory: 'inventory',
  capacity: 'capacity',
});
```

左边是 URL 第一段/应用 ID，右边是 apps 下的产物目录。本项目静态接入统一使用 `id = 目录名`、`url = /<id>/`。不能只改 apps.json 而不加映射。

从门户根目录启动：

```powershell
npm run dev:static -- --port 4176
```

先打开 `http://127.0.0.1:4176/capacity/` 验证实际页面，再验收门户中的 `http://127.0.0.1:4176/#/app/capacity`。不要双击 HTML 代替同源验收。

### 4.3 准备打包配置

复制并核对 `deploy/config.example.json`，本机配置放在被忽略的 `deploy/config.local.json`；保留已有静态应用，在 `StaticApplications` 数组中加入以下对象：

```json
{ "Name": "capacity", "Enabled": true }
```

打包器按此清单复制 `apps/capacity`，不会因为 apps.json 新增条目就自动包含文件。静态应用需要同时核对：

| 文件 | 作用 |
|---|---|
| `portal/config/apps.json` | 菜单、名称、状态、公共地址 |
| `scripts/dev-server.mjs` | 本地 URL 到发布目录的映射 |
| 实际使用的 IIS 配置 JSON 的 `StaticApplications` | 打包与服务器静态应用清单 |
| `apps/<id>/` | 实际发布产物 |

以下仅检查打包输入并展示计划，不写入发布包或 IIS；目标应为新的版本目录：

```powershell
powershell -NoProfile -ExecutionPolicy RemoteSigned -File .\deploy\New-DeploymentPackage.ps1 -ConfigPath .\deploy\config.local.json -Destination .\staging\Review-capacity-v1 -WhatIf
```

这条命令**不包含 SOP 发布程序**。完整交付若需要 SOP，应按 [README](../README.md) 从 SOP 原项目生成新产物，并使用 `-IncludeSop -SopReleasePath $sopRelease`；该变量由相对产物目录解析生成。不要拿不含所需服务的包替换整套运行环境。

生产由管理员将 `/capacity/` 建为独立 IIS Application，物理目录放在门户站点根目录之外的应用目录。不要用 `Install-IisSite.ps1` 给已存在站点“追加应用”：它用于新建站点，会拒绝已有站点/应用池。现有站点的变更需另列具体计划，由管理员按授权执行。参见 [IIS 部署指南](iis-deployment.md)。

## 5. 动态服务怎么接

动态应用除了页面，还需要原项目服务、数据配置和代理。不得复制 web 目录冒充完整应用，也不在 apps.json 填 `http://127.0.0.1:8501/` 之类后端地址。

1. 只读核对原项目的现有启动与配置接口，按已有能力运行独立服务；服务监听受控回环地址，端口不能与其他应用冲突。不支持的能力列为阻塞，不在门户任务中修改原项目。
2. 明确公共前缀与代理策略，整条链只使用一套约定：

   | 浏览器请求 | 保留前缀时后端收到 | 剥离前缀时后端收到 |
   |---|---|---|
   | `/capacity/api/state` | `/capacity/api/state` | `/api/state` |

   无论哪种策略，浏览器获得的资源/重定向/Cookie 地址都必须落在公共前缀内。
3. API、上传、导出、WebSocket 都经过同源入口。WebSocket 应专项验证，首页 200 不代表连接正常。
4. 数据库、上传和日志保留在非静态目录；密钥放服务器环境变量或受保护配置，不能写入公开注册表、前端或 Git。
5. 部门成员统一使用已有业务功能，门户不新增角色、写入域组或逐用户授权，也不改变子应用已有的权限规则；出现差异时记录并交由独立任务处理。保留入口的部门访问边界；仅隐藏按钮、菜单或设置 enabled=false 都不构成访问控制。可信身份用于操作留痕，由受控代理覆盖客户端伪造身份头，后端验证代理来源。全服务维护开关可以暂停所有人的写入，不按成员分级。
6. 为生产准备独立服务的启动、停止、重启恢复、日志和发布/回退说明。不要依赖个人终端窗口长期运行。

### 当前动态预览的实际边界

`npm start` / `npm run dev` 启动原 SOP 并使用可操作的隔离数据快照（不回写原项目，重启创建新快照）；`npm run dev:sop` 可使用演示数据。**它们都不是任意新后端的通用启动器。**

当前 `createServer` 只提供 SOP 的专用本地桥接。新动态应用需另行实现受控的同源预览代理，或在获授权的 IIS 测试环境完成接入。新增代理时同步调整相应脚本、配置校验和测试；不要复用 SOP 的身份头、密钥或业务源码，也不要改成允许任意目标 URL 的开放代理。

如果尚无同源测试入口，先完成现有能力核对与门户接入计划；原项目缺失能力只列为待办，注册状态保持 pending，明确记录尚未验收；不能为“先看到页面”而放宽门户同源校验或 CSP。

### SOP 与通用代理示例的区别

- `deploy/arr-rules.example.xml` 仅以 leads 演示剥离前缀；不是新服务的即用配置，更不是 SOP 配置。
- SOP 保留 `/sop/` 前缀，使用原项目 gateway 和认证后的 IIS 身份模块。
- 现有通用打包器没有自动收集任意新动态应用的能力；应明确新应用的独立发布流程，或补充经过验证的通用部署支持。不要将业务源码纳入门户来绕过此限制。

细节见 [SOP 内网部署](sop-intranet.md) 与 [IIS 通用部署](iis-deployment.md)。不要自动修改 IIS、认证、ARR 全局开关或安全设置。

## 6. 登记应用入口

在 `portal/config/apps.json` 的目标分组 `apps` 数组加入或更新应用对象。下面是合法对象，**不是完整配置文件**，不能拿它覆盖整个 apps.json：

```json
{
  "id": "capacity",
  "name": "产能分析",
  "subtitle": "Capacity",
  "description": "查看产能安排，辅助制定未来入库计划。",
  "url": "/capacity/",
  "icon": "chart",
  "enabled": true,
  "status": "pending",
  "version": null,
  "dataUpdatedAt": null
}
```

若新增分组，其结构如下；group ID 也须唯一：

```json
{
  "id": "supply",
  "name": "供给协同",
  "apps": []
}
```

| 字段 | 当前实现的含义 |
|---|---|
| `id` | 全局唯一；顶部导航和 hash 路由的依据 |
| `url` | 同源根相对子路径，必须带末尾 /；无外域、查询参数、编码路径、.. 或重复斜线 |
| `enabled` | 是否在导航/首页显示；不是服务开关或访问权限 |
| `status` | pending：待接入；ready：可打开；maintenance：维护中。pending 与 maintenance 状态页不会请求业务页面 |
| `icon` | 使用 chart、box、calendar、trend、users、grid；未知值回退 grid |
| `version` / `dataUpdatedAt` | 可保留元数据；当前界面不显示应用版本和更新时间，不应恢复底部文字 |

`status: ready` 是接入完成标记，不是实时健康检查。先通过验证再切 ready；有意在本地临时切 ready 验收时，未通过就恢复 pending，并明确本地与内网验收范围。不能仅因 npm run check 通过就宣称已经上线。

`platform.defaultApp` 只能为 home 或已启用的 ready 应用 ID。`platform.loadTimeoutMs` 默认 20000，允许 1000–120000 毫秒。新增应用不需要手写顶部标签或复制首页卡片，门户会按配置生成；SOP 保持优先位置。应用增多时验证顶栏和窄屏展开菜单，必要时改进通用布局，不另加侧边栏。

## 7. 验证与排查

```powershell
npm run check
npm test
```

`npm run check` 校验注册表、JavaScript 语法，以及映射清单中 ready 静态应用的 index.html；对非静态应用只给提示，不能证明服务、API、权限或 IIS 已通过。若修改挂载/代理，应补充有实际意义的路由、错误和隔离测试。

| 验收项 | 通过标准 |
|---|---|
| 独立页面 | 直接打开公共子路径、刷新深层路由、资源与接口正常 |
| 门户打开 | 正确高亮；切换应用、前进/后退、回工作台正常 |
| 首页 | 名称/用途正确；搜索、分组、待接入与无结果状态正确 |
| 异常恢复 | 404、401/403、服务停止、超时、禁止嵌入时说明合理；失败重试可用，正常态无额外工具条 |
| 业务功能 | 用测试数据验证导入、导出、上传、下载、打印、存储、Cookie 和必要写 API |
| 访问与操作 | 验证部门成员均可查看、维护、导入导出；未获准进入部门入口的访问应被拒绝；直接应用 URL 不绕过入口，操作人正确留痕 |
| 数据与运行 | 原数据路径不变；静态 URL 无法下载数据库/规则/密钥；服务重启可恢复 |
| 布局与风格 | 桌面、手机、键盘焦点正常，无整页横向溢出，保留截图，遵循设计基准 |

门户先 HEAD 探测再加载 iframe，HEAD 返回 405/501 时仍尝试 GET。页面最终地址必须留在约定应用前缀内。iframe 的 load 只代表文档加载，不能代替业务 API/数据验收。

常见问题：

- 菜单有、页面 404：检查实际产物、本地 STATIC_APPS、IIS Application 或代理规则；只改注册表不会创建这些。
- 页面白屏/资源 404：检查构建 base、绝对资源路径和子路由回退；看控制台，不用全站 fallback 掩盖问题。
- 无法嵌入：检查应用最终响应头及继承的 IIS 配置。
- 页面能看但不能操作：检查接口前缀、全局维护开关、身份/Origin/代理校验与业务端错误，不再要求额外写入域组。
- 老页面仍显示：核对实际服务/构建版本与缓存；版本化静态资源，必要时强制刷新。不要误改历史 staging 包。

## 8. 交付与后续更新

交付时列出：门户改了哪些文件，并核对原项目受控文件未被本任务修改；源码版本/发布产物来源；数据路径；可执行启动命令；已验证内容和截图；未完成的内网权限/运维事项；回退方法。

相关必要检查通过后，默认仅在门户仓库创建 Git 提交，并推送到当前分支已配置的上游；只提交本次任务相关文件，核对远程和分支，不强制推送。报告短提交号和推送结果；推送受阻时保留提交并说明具体原因。默认推送不包含部署授权。

后续业务更新先在**原项目**修改并验证，再构建新产物或更新独立服务；门户只更新必要的注册和接入配置。不从 apps 或旧 staging 目录反向维护业务源码，不重写 Git 历史。

静态应用的 `apps/*/`、本机配置、数据和发布目录已被 Git 忽略。忽略不等于访问保护：真实数据进入报表 HTML 后仍可能被浏览者看到；不要把含业务数据的产物公开上传。

本指南不授权部署、改仓库可见性或修改 IIS/安全设置。先把代码、配置草案、验收记录和回退方案准备到可审阅状态；生产操作需要另有明确授权。
