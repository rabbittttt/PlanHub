# 应用接入手册

本手册供内网网页开发者及其 AI 使用。源码无需传到外网电脑，按下列约定在内网完成交付即可。

<a id="integration-boundary"></a>
## 共同边界

门户只登记入口、挂载静态文件或转发独立服务。业务源码、UI、数据、权限和算法在原项目维护；门户不注入脚本、不改 iframe 内容、不重写页面响应。需要子项目适配时，交由原项目任务处理。

<a id="portal-integration"></a>
## 新增网页：双击向导

在内网开发电脑把业务项目放到门户旁边，双击门户根目录 `接入新网页.bat`。

静态示例：

```text
应用 ID：capacity
导航名称：产能分析
类型：1 静态
发布目录：../产能分析/dist
入口文件：index.html
额外公开资源：assets/
```

单 HTML 没有额外资源时留空。向导会核对文件，登记导航和本机挂载，并在 `artifacts/registration-*` 保存原配置。先停止再启动开发门户，手动打开 `/#/app/capacity` 检查。正式 Docker 运行绑定另见下方，不再生成 IIS 配置。

动态网页选择类型 2，登记原项目公开默认端口、健康地址（例如 `/healthz`）、返回 JSON 字段、工作目录、解释器、启动参数及必要环境变量。默认启动探针只检查稳定字段；需要复用已有服务时，可在 apps.json 设置 healthExpected 核对身份、公共前缀等固定值，避免误用其他实例。参数按数组填写，例如 `["-B","server.py","--port","{port}"]`。{port}/{host} 来自门户 target，{basePath} 为 /应用ID/；可用于启动参数、环境变量和健康身份期望。未知应用的端口参数名称仍按原项目契约填写。原服务尚未验收时保留 pending，验收后再次运行向导更新同一 ID。

接入登记与子项目公开默认端口保持一致，门户通过公开启动参数传入登记值。已有应用的默认端口只维护在 `integration/ports.json`；`integration/apps.json` 的 `target` 使用 `{port}`，启动与健康配置继续使用上述占位符。本机 `config.local/` 的数字 `target` 仍可明确覆盖开发联调地址，但不改变正式发布登记。动态配置中的路径相对门户根目录；环境变量值由原应用解释，通常相对业务工作目录。不要填写某个开发者的盘符和用户名。向导登记不会构建、启动或修改业务源码。

子项目维护者修改默认端口时，同步 `integration/ports.json`，无需在联调和发布配置中重复填数值；门户不解析业务代码猜测端口。新动态应用先由向导登记本机接入，正式发布前还须补齐该端口登记及下方发布绑定。原项目的独立启动规则仍由其维护者管理。

若希望让内网 AI 自动填写，可保存下面配置后运行：

```powershell
node scripts/register-app.mjs --config config.local/new-app.json --dry-run
node scripts/register-app.mjs --config config.local/new-app.json
```

```json
{
  "id": "capacity",
  "name": "产能分析",
  "type": "static",
  "root": "../产能分析/dist",
  "entry": "index.html",
  "publicPaths": ["index.html", "assets/"],
  "order": 45
}
```

更新已有 ID 需加 `"replace": true`。向导合并修改导航和本机挂载，其他应用设置保留。SOP 的已有身份网关继续用专用配置，不通过通用向导替换。

## 开发者交付五项内容

| 项目 | 静态网页 | 动态网页 |
|---|---|---|
| 完整产物 | HTML 与全部资源 | 同版前后端、依赖清单 |
| 固定入口 | `/<id>/` | `/<id>/`，所有 API 同样在此前缀内 |
| 原项目命令 | 构建或生成命令 | 构建、启动、正常停止方式 |
| 持久数据 | 页面内数据随报表交付 | 数据库、上传、Excel、设置在版本目录外 |
| 验收 | 页面、资源、嵌入、下载 | 再加健康接口、查询、导入导出、保存后重启 |

只交前端文件不足以部署有后端的应用。Python 发布包可以含运行需要的 `.py`，但不应包含整个开发仓库、Git 历史、虚拟环境、测试、日志、密码或业务数据库。静态报表也可能含真实业务数据，不上传公开仓库。

## 页面必须满足的约定

- 应用 ID 唯一。浏览器访问地址固定；内部新标签、新 API 无需门户逐项登记。
- 资源、API、跳转和下载均在 `/<id>/` 内。支持前缀配置，不能抢占站点根 `/api/`、`/assets/`。
- 同源 iframe 可打开。原项目负责合适的 CSP、Cookie Path、来源校验，不强制跳出门户。
- 服务存活接口应轻量、只读，建议返回稳定 JSON，不依赖是否已有业务数据。需要区分数据等待或生成失败时另设就绪接口，未就绪返回非 2xx。不要用业务标题或重型数据扫描当存活探针。
- 前台启动，监听可配置的回环端口。路径从明确基准解析；允许运行时指定数据目录。
- 新旧程序切换使用同一份正式数据。不得启动时重置，也不同时启动两版写同一数据库。
- 静态应用当前支持 HTML/CSS/JS/JSON、常见图片及字体；用明确公开清单。SPA history 回退、WebSocket 等特殊能力需单独确认，不能假定自动支持。

各应用的默认目录及入口见[项目首页](../README.md)。首次部署参数见[部署手册](deployment.md)。

## 发布与验收

更新代码后双击 `发布应用.bat`，选择应用，工具自动调用原项目构建入口并校验版本包，具体操作见 [部署手册](deployment.md)。A 制作普通文件夹，首次附带 Windows 运行环境，后续可只打程序；不要求 A 或 B 预装 Docker。B 可先本机试运行；部署同事后续使用同一份应用产物构建 Docker 镜像。构建入口应直接从当前源码生成同版前后端，不依赖开发机历史报表或正式业务数据；静态应用收集首次已登记的真实发布文件。发布包不可覆盖，版本与数据分开；程序更新和数据刷新是两条流程。正式版本只使用已验收产物。

验收至少检查页面、全部资源、子路径、同源嵌入、关键查询与下载；动态应用再检查保存、导入导出和重启持久化。门户侧执行 `npm run check`、`npm test`。配置检查通过不代表业务验收或内网部署完成。

<a id="portal-ai-task"></a>
## 发给业务开发者 AI

> 在本业务项目提供可重复生成的独立发布包，配套前后端、稳定公共前缀、轻量健康接口、可配置端口和外置持久数据。保留独立运行与同源嵌入。说明构建/启动命令、依赖和数据路径基准，验证保存、导入导出、重启及版本切换。业务源码只在本项目维护，不改门户或其他项目。门户按固定前缀转发，内部新增页面与 API 不需要逐条登记。交付到内网即可，无需把源码传出内网。

## 发给门户维护 AI

> 使用本手册登记内网应用。仅修改门户配置及通用工具，优先复用 register-app 和发布工具；不修改业务源码、页面、权限或数据规则。路径保持可迁移，不把实际数据与本机配置提交 Git。无法访问真实网页时说明已验证范围，不把替代样例验收当成正式业务验收。

<a id="current-contracts"></a>
## 当前版本核对（2026-11-12）

- **车型配置**：动态服务 `/vehicle-config/`，开发源码 `../配置管理`，健康接口 `/healthz`；`scripts/build_release.py` 生成独立通用包。Docker 显式启用 `--require-proxy-identity`，保留原有 `X-Config-User`、`X-Config-Proxy-Key` 及 ASCII 操作人契约，不使用容器账号冒充业务用户。

- **SOP计划管理**：继续使用原网关、整段 /sop/ 代理与原构建器；业务新增标签不需门户逐项登记。新版计划保存在数据库，Excel 从页面导出、修改后导入；服务器旧维护表仅归档，不再自动同步。正式资料对账来源通过 SOP_RECONCILE_DIR 指向 shared/对账资料。
- **订单分析**：动态服务 /orderiq/，健康接口 /health。本地沿用原项目的数据选择；正式部署显式传 --input、--data-dir、--state-dir、--web-dir。原 Git 仓库在订单分析/scripts，构建入口 generate_html/package_release.py；直接从同版模板生成发布前端，不依赖 Excel、旧 runtime 或已生成批次。业务数据由部署后的原服务处理，打包无需先运行 main.py。
- **数据速查**：动态服务 /quicklook/，健康接口 /healthz；新版自动扫描使用 SHARED_DATA_ROOT，工作区来源的相对路径仍由 DATA_QUICKLOOK_SOURCE_BASE 解释。
- **线索声量**：当前可见交付仍是 lead-dashboard.html 静态样例。若内网已改动态，在内网重新运行接入向导更新同一 leads ID，再配置该项目发布包；不能将样例当作正式动态验收。
- **销量预测**：动态服务 /forecast/，dynamic/serve.py 启动；scripts/build_release.py 构建标准包。--public-prefix 配置公共前缀，--data-dir 或 SALES_FORECAST_DATA_DIR 外置页面、缓存和日志，SHARED_DATA_ROOT 指定共享输入。/healthz 只检测服务，/readyz 区分首次等待、就绪与生成失败；/api/status 提供更新状态。首次生成前页面自动等待，不把尚无报表当成进程启动失败。静态入口仍可在原项目独立使用。

SOP 的接入说明与协作约定已同步当前实现：门户默认使用持久数据库，Excel 从页面导入导出，仅显式 --snapshot 才使用测试副本。

<a id="docker-contracts"></a>
## 发布包、本机验收与 Docker 集成

发布步骤只维护在 [部署手册](deployment.md)。A 的交付文件夹包含原样校验的应用发布包、本机试运行和后续 Docker 构建工具。菜单 `0` 为全部七个应用加 Windows 运行环境，首次交付使用；菜单 `8` 为全部应用但不附带 Windows 环境，可用于后续本机测试或 Docker 部署。自动化可调用 `deploy/Publish-App.ps1 -All -WithoutRuntime`。选 `8` 仍调用各原项目构建入口，需要 A 的开发依赖，只省去环境收集与传送。打包阶段不制作镜像、不调用 Docker。交付工具和顶层目录使用英文名，子应用原包内部文件名不改写。

Node.js 完整许可证从运行程序所在目录读取（支持文本和 RTF）；缺失时使用 `deploy/licenses/node/index.json` 登记的同版本官方离线文件，不在内网打包时下载。维护者新增离线版本时须保留完整第三方声明、官方来源和 SHA256；许可证原始字节由 `.gitattributes` 保留。发布前先预检，普通打包人员无需手工补许可证。

全部应用交付包提供 `prepare.cmd` 创建包外的 `planhub-runtime/`，提供 `preview.cmd` / `stop-preview.cmd` 在 B 本机验收。选 `0` 使用随包 Windows 环境；选 `8` 自动查找并校验同层旧完整包的环境和依赖兼容性，复用原文件，不要求用户手填路径、复制环境或安装软件。找不到兼容环境须明确报错并提示重新选 `0`。两者均不依赖 A 的源码或 B 预装 Node.js、Python、Docker。首次运行将规则、共享输入和应用状态复制到独立的 `planhub-preview/`；共享输入也需复制，因为销量预测可能写入派生表。复制前须停止原数据服务，避免复制正在写入的数据库。试运行公共入口为 `127.0.0.1:4173`，以 B 实际 Windows 用户标识记录操作人（登录名不符合现有传输字符契约时记录该用户的真实 SID）。预览数据与正式目录独立，不合并。

后台默认端口统一登记在 `integration/ports.json`，与子项目公开默认端口一致。开发联调和发布构建都从这里取值；源码 `deploy/docker/bindings.json` 只维护启动、路径和健康契约，打包后生成包内带具体端口的 `bindings.json`，不得在 B 手改。本机试运行先尝试该默认端口，只有占用或无法绑定时才选择空闲回环端口。实际端口只记录在当前快照的 `native-ports.json`，启动参数、健康检查和门户代理共用，不修改不可变发布包、源配置或子项目默认值。未知进程不复用、不停止。公共入口 `4173` 固定，冲突时先停止原门户，不自动换号。Docker 使用生成绑定中的容器内固定端口；只发布门户端口，本机试运行和正式服务不可同时占用宿主 `4173`。

已有测试副本时，双击 `preview.cmd` 会提供两项：`1`（回车默认）保留当前测试数据、共享数据和配置，仅更新程序；`2` 从已准备的 `planhub-runtime/` 新建副本，旧副本保留。`-RefreshSnapshot` 直接选择后者。兼容的程序版本或后台端口变化沿用原副本；选择保留时不会因正式源文件有变化而重新复制。应用清单或运行契约不兼容仍须报错核对，不能跳过来源、身份和路径检查。用户操作步骤统一见[后续更新](deployment.md#updates)。

旧 `4174` 副本先通过归属校验停止，再更新该副本的公共地址与端口为 `4173`，原数据和正式 `planhub-runtime/config.json` 保留。

后续由部署同事安装并检查 Docker，运行包内 `build-docker.cmd` 构建镜像，再用 `start.cmd` 正式部署；构建需要可用的基础镜像及 Python 依赖源。Windows 本机验收不能替代 Linux 容器业务验收。门户和每个应用各自一个镜像、一个容器；网络辅助容器只保留共同网络空间，使现有回环监听与 SOP 回环信任条件保持有效。只有门户端口对宿主开放，应用按整段前缀代理，业务文件按原清单校验并原样装入镜像。

容器启动参数、路径和健康身份集中在源码 `deploy/docker/bindings.json`，端口来自唯一登记文件；新增应用须登记两者并核对原项目在 Linux/Python 3.12 下的支持情况，不能假定原生 Windows/COM 依赖能进入 Linux 镜像。B 的环境配置只在外置 `planhub-runtime/config.json`；所有相对路径均以该运行目录为基准，在容器中统一挂到 `/runtime`。运行镜像只读，没有源码热更新。

| 内容 | 外置路径及首次迁移注意事项 |
|---|---|
| 共享输入 | `shared/` 下保留原业务目录，例如 `订单汇总`、`对账资料`；销量预测可能更新共享派生表，不能全部只读 |
| SOP | `data/sop/` 为持久数据库；`config/shared_config.py` 必须是真实规则；旧维护 Excel 不再自动同步 |
| 订单分析 | `data/orderiq/runtime/` 与 `data/orderiq/annotations/`；前端来自镜像，输入来自共享订单目录 |
| 销量预测 | `data/forecast/`；存活健康与生成就绪分开，`/forecast/readyz` 才表明报表可用 |
| 数据速查 | 本次交付不沿用旧数据速查文件，`data/quicklook/` 从空目录开始，由服务创建数据库并处理共享来源及新上传。配置内部保留默认 `quicklookSourceBase=shared`，无需部署人员修改。一般技术边界：该值只解释工作区相对路径，不转换旧库中的绝对文件路径；另行迁移旧库时仍由原项目处理 |
| 车型配置 | `data/vehicle-config/`；首次由部署同事核对原共享目录中的真实持久数据，不用空目录代替迁移 |

后续版本继续使用同一 `planhub-runtime/`，只更新程序时不重复迁移数据或覆盖配置；数据、共享文件或配置也要变化时，由同事停服、备份并按本次需求明确修改。新旧程序文件夹并排保留，不覆盖版本产物；用 `8` 本机测试时保留供其复用环境的旧 `0` 包。全部应用包（`0` 或 `8`）更新切换整套容器；单应用包只更新该容器，要求已有完整部署、环境配置未变且运行契约兼容。本机试运行必须使用全部应用包。不要用另一个 Compose 项目名同时运行第二套服务写入相同目录。重启策略不代替 Docker 宿主开机配置和重启验收。

公司入口负责认证，门户只校验约定的可信代理密钥并转发真实操作人。密钥在 B 首次准备时生成，后续不轮换、不进镜像、不进仓库；SOP 和车型配置仍使用各自原有密钥接口。业务验收必须检查真实操作人，容器健康检查使用只读健康身份，不代表用户登录。
