# 应用接入手册

适用对象：子网页开发者、门户维护者及其 AI。整理日期：2026-11-05。本文合并原开发者规范、门户接入指南、集成边界和 AI 任务模板；保留本文件地址，之前分享的链接继续可用。

**你们继续在自己的项目中开发和发布，门户只提供统一入口、静态挂载或独立服务代理。接入不会自动修改业务 UI、算法、数据口径或权限。日常维护结果必须持久保存，服务或门户重启后继续使用。**

<a id="integration-boundary"></a>
## 职责边界：双方分别维护自己的项目

- 门户任务可以改门户外壳、首页/导航、入口注册、接入配置、通用启动、代理、打包及验证；可以只读核对原项目，并使用其已有公开参数及原样发布物。
- 门户任务不得修改子应用源码、UI、文案、图标、业务逻辑、权限、数据规则、测试或协作规范，也不得注入、裁剪、改写 iframe/代理正文或剥除安全响应头。
- 日常操作通过原项目服务持久保存数据；这不授权门户开发任务直接篡改业务数据。验收使用明确的测试数据，保留正式数据和恢复备份。
- 接入遇到不支持的子路径、嵌入或身份能力时，先列具体表现、相关文件及必要改动，保留 pending 或明确受限范围；经单独授权后，由原项目任务处理。不得以“接入必须”为由直接覆盖。
- 用户已确认保留此前完成的子应用改动，今后严格分开；原项目历史适配记录见[历史档案](history.md)，不构成新的修改授权。
- 门户供部门内部使用，正常成员使用相同业务功能，不新增只读/可写角色或写入域组；原应用有自己的规则时先核对差异。保留来源校验和可信操作人记录，隐藏导航不能代替入口访问控制。
- 默认提交推送只覆盖本次授权的门户文件，不扩展为对子应用仓库的修改/提交权限。部署、IIS/安全配置和仓库可见性变更需另有明确授权。

<a id="developer-contract"></a>
## 1. 最先确认的六条规则

1. **源码独立**：保留自己的项目、仓库、依赖、测试及启动方式；交付发布物或独立服务，不将整套业务源码放进门户维护。
2. **应用路径独立**：与接入方确定唯一 ID 和公共前缀，例如 `capacity`、`/capacity/`；浏览器页面、资源、接口、跳转和下载均留在该前缀内。
3. **允许同源嵌入**：页面可以直接访问，也能在门户同源 iframe 中使用；不依赖门户修改页面正文或操作 iframe 内的 DOM。
4. **可以迁移**：磁盘路径从项目位置或显式配置解析；域名、服务端口、数据位置可配置，不能依赖开发者电脑的盘符、用户名或临时目录。
5. **数据持久保存**：原项目或明确的数据目录负责数据库、维护表、上传及配置；门户不为日常操作建立每次启动即更换的业务副本。
6. **提供可验收交付**：说明启动/构建方法、数据路径、前缀策略和所需能力，并提供测试数据，完成页面和关键业务操作的验收。

## 正式发布契约（所有应用及开发者 AI 必读）

2026-11-10 确认采用 **独立发布包 + 独立服务 + 固定入口**。门户只提供外壳与转发；开发项目中新增标签、改布局、增加前缀内接口，无需同步修改门户。只有公共前缀、监听地址、启动方式或嵌入契约变化，才需要协商接入配置。遗留数据速查根 API 的兼容清单不作为新项目范例。

开发目录与正式发布目录必须分开。动态应用每次交付同一版本的前端、资源、后端和依赖说明，不能只更新 HTML，仍运行旧后台。发布目录不作开发修改，也不从开发目录动态读取 Python/JS 模块。门户不会监视源码、猜测新增接口或在有人保存数据时自动重启应用。

通用格式为 `app-release.json` 和 `payload/`。元数据包含 schemaVersion=1、appId、version、type（static/service）、basePath、entryPoint、sourceRevision、dataMode（external/stateless）、healthPath、files（path/bytes/sha256）。路径使用相对值；静态入口为 index.html。文件清单声明整个版本，文件改动、缺少、混入或越界均会被拒绝。哈希证明交付内容一致，不能代替发布方的来源审核与功能测试。

原项目先完成构建、依赖及业务验收，准备仅含运行产物的目录，然后可使用门户提供的通用封装工具。它只原样复制产物和生成元数据，不编译、不执行应用、不修改原目录：

```powershell
# 示例新应用，实际 ID 须与门户注册表一致；路径从门户根目录运行。
./deploy/New-AppRelease.ps1 -PayloadPath ../产能分析/dist -Destination ./staging/capacity-v1 `
  -AppId capacity -Version v1 -Type service -EntryPoint server.py `
  -SourceRevision '<原项目实际提交或构建版本>' -DataMode external -HealthPath /health -WhatIf
# 检查计划后去掉 -WhatIf 创建新包；目标目录已存在时拒绝覆盖。
```

动态应用的数据库、上传、配置、维护表与备份必须通过自己的公开参数或配置放在版本目录外。dataMode=external 是发布方的契约声明，封装器无法证明应用实际写入路径；必须验收“切换两个版本仍读到同一份持久数据”。无持久状态才可声明 stateless；静态报表用 stateless 不代表报表内没有业务数据。不得为通过校验谎报模式。

独立服务交付清单还应给出运行时、启动命令、工作目录、外置数据配置和停止方法。健康检查仅用于验证服务是否就绪，使用稳定的轻量 HTTP 地址；不要依赖会随标签改动而变化的标题或业务字段。业务 API 诊断与启动探针分开。发布期间只停对应服务，等待写入与后台任务结束，切换全套版本后启动、验证并刷新页面；旧页面与新 API 兼容性仍由应用负责。

SOP 继续接受原项目的 sop-release.json，无需改格式。订单分析和销量预测由现有收集器取原样静态产物，门户打包时补充版本清单。数据速查当前 server.py 把数据库及设置固定在 ROOT/output_file，尚不满足版本外持久数据契约；应由其原项目另行提供数据目录参数和完整发布产物。在此之前不得直接把新包目录作为新的数据位置上线。另有 `web/app.js` 使用根 `/api/`，新接口仍依赖门户兼容清单；原项目需支持可配置公共前缀，让浏览器请求落在 `/quicklook/` 内，才能做到新增接口无需修改门户代理。门户不通过注入脚本或全站 `/api/` 抢占来绕过这一差异。

发布封装和新应用服务安装是两件事：通用包不会自动注册 Windows 服务、修改 IIS、安装运行时或生成每个应用的专属启动参数。正式发布、单应用升级和回退见[部署指南](deployment.md#通用应用发布与完整交付检查)。

## 2. 选用哪种接入方式

| 项目类型 | 开发者交付什么 | 门户如何消费 |
|---|---|---|
| 单文件 HTML 报表 | 原项目生成的 HTML、生成命令和来源版本 | 挂载原 HTML，或收集到忽略的发布目录 |
| 多文件静态网页 | 完整发布目录，包括 HTML、JS、CSS、字体、图片等 | 只挂载声明可公开的发布文件 |
| 带 Python / Node 等后端的应用 | 独立服务、依赖清单、启动参数、健康检查与数据位置 | 运行或复用服务，通过同源前缀代理访问 |

若页面需要 API、数据库或上传功能，不能仅交付前端文件就声称应用已完整接入。静态报表中已嵌入的数据也属于公开给访问者的页面内容，不能把真实报表上传到公开 Git 仓库。

## 3. 浏览器地址与资源、接口规则

### 3.1 三种路径要区分

以下文件系统路径以**门户根目录**为基准；你们项目自身配置中的相对路径应明确以**自己的项目根目录**为基准。

| 用途 | 示例 |
|---|---|
| 独立项目磁盘位置 | `../产能分析/` |
| 浏览器业务公共地址 | `/capacity/` |
| 门户导航地址 | `/#/app/capacity` |

门户导航地址不是业务页面地址。不要将 `file:///...`、后端的 `http://127.0.0.1:某端口/` 或某台电脑的 IP 写进页面作为业务入口。

应用 ID 使用小写字母开头，只含小写字母、数字和连字符；新应用统一约定 `/<id>/`，保留末尾斜线。IIS 静态应用名最长 40 个字符。避开 `home`、`sop`、`api`、`assets`、`css`、`js`、`config`、`data`、`logs`、`services`、`scripts`、`deploy`、`tests` 等已有或保留名称；分组 ID 的 `all` 也保留。先与接入方核对，不重复注册已有应用。

### 3.2 子路径必须贯穿整个页面

推荐资源地址为 `./assets/app.js` 或带正确公共前缀的 `/capacity/assets/app.js`；API 访问 `/capacity/api/...`。以下内容均需核对：

- CSS、JS、字体、图片、favicon、懒加载资源及动态 import。
- fetch/XHR、表单提交、文件上传、导出下载和打印资源。
- 登录返回、HTTP Location、页面内部链接、Cookie Path 及服务工作线程作用域（若使用）。
- SPA 的路由 base、刷新深层路由和直接打开书签地址。

不要让各应用争用站点根部的 `/api/`、`/assets/`、`/static/` 或 `/login/`。数据速查已有精确根 API 转发，是保留原实现的兼容方案，不是新应用的默认开发方式；同名根接口冲突不会靠 Referer 猜测分流。

如果需要同时保留独立运行与门户运行，使用原项目自己的构建或运行配置来选择公共前缀。例如由原项目生成不同的 `app-base` 元数据，前端按它构造地址：

```html
<!-- 门户模式；独立根路径运行时由原项目输出 content="/" -->
<meta name="app-base" content="/capacity/">
```

```js
const appBase = new URL(
  document.querySelector('meta[name="app-base"]').content,
  location.origin
);
const response = await fetch(new URL('api/state', appBase));
```

这是可采用的实现示例，不是门户自动注入的配置。仅将资源写成相对路径并不能解决 SPA 深层路由的基准问题，需要在自己的构建、路由和服务中一起核对。

### 3.3 允许同源 iframe

公共页面与门户需使用相同协议、主机和端口。最终 HTML 响应不得包含禁止嵌入的策略；通常可使用以下 HTTP 响应头：

```http
X-Frame-Options: SAMEORIGIN
Content-Security-Policy: frame-ancestors 'self'
```

与应用已有 CSP 合并，不要用这两行覆盖其余安全策略；`frame-ancestors` 应由 HTTP 响应头下发，不能依赖 HTML meta。不要在页面中强制 `top.location` 跳出门户。门户不会剥除子应用的响应安全头。

建议实现正确的 HEAD 响应。门户先 HEAD 探测页面，再 GET 加载 iframe；HEAD 不支持时应明确返回 405/501，不能无限等待、返回伪 200 错误页或重定向到前缀外。

## 4. 文件与数据路径：换电脑仍能运行

建议保持类似布局；文件夹名称仅为示例，不要求迁移现有项目来凑目录：

```text
工作区/
  计划工作台/       # 门户
  产能分析/         # 你们自己的源码、发布物及私有数据
  共享数据/         # 已明确归属的共用输入
  .venv/            # 若使用工作区共享 Python；换电脑重新创建
```

- 以脚本/项目位置解析默认路径，不能依赖“必须先 cd 到某目录”。命令行覆盖值和配置文件相对值的解析基准应写入项目说明。
- 分开代码、公开发布目录和持久数据目录；数据库、原始 Excel、日志、机密及临时上传不得落入可下载的静态目录。
- 页面读取服务器文件应通过业务 API；浏览器不能直接访问服务器磁盘路径。
- 共用 Excel 时声明谁负责写入、谁只读以及更新触发方式，不要求为接入合并各项目数据库或计算口径。门户目前不是自动“上传一次供全部应用导入”的数据中心。
- 保存计划、修改设置及导入数据应写入明确的持久目录。启动、重启或升级不能重新用默认种子覆盖已维护数据；演示/测试模式需显式选择。
- 说明服务停止、门户切换页面、浏览器关闭、重复请求、并发修改及 Excel 占用时的保存行为。重要维护数据不能只放内存或未持久化的前端状态。
- `localStorage`、IndexedDB、CacheStorage、Cookie 应使用应用专属名称，例如 `capacity:views:v1`，避免同源应用互相覆盖。Cookie Path 与 Service Worker scope（若使用）也应限制在应用前缀，不接管门户或其他应用。浏览器收藏/草稿属于浏览器存储；切换独立地址到门户地址或换电脑，不会自动迁移。需要部门共享的数据应在业务服务端保存。
- 业务数据、密钥、日志和真实报表不提交公开 Git；备份、恢复和数据迁移方式由原项目说明。不要复制旧电脑的 Python 虚拟环境到新电脑。

## 5. 静态网页交付要求

发布目录只包含浏览器使用的文件，保留资源目录关系。给出入口文件、公开文件清单和可重复执行的构建命令；交付来源版本或文件哈希，不让接入方猜哪个 HTML 是最新版。

下面是给门户接入方的配置示例，需**合并到现有 applications 中**，不能覆盖门户已有应用：

```json
{
  "applications": {
    "capacity": {
      "type": "static",
      "root": "../产能分析/dist",
      "entry": "index.html",
      "publicPaths": ["index.html", "assets/"]
    }
  }
}
```

`root` 相对门户根目录；`entry` 和 `publicPaths` 相对发布目录，使用 `/` 分隔、不含 `..`。公开子目录以 `/` 结尾，不使用 `*` 通配。前缀内的文件也必须在公开清单和 MIME 白名单内才可访问。

当前静态预览与收集工具支持 `.html .css .js .mjs .json .svg .png .jpg .jpeg .gif .webp .ico .woff .woff2 .txt`。PDF、CSV、WASM 等尚需门户另行补充并验证支持；不要假定所有扩展名都会被提供。发布物使用真实文件，收集工具拒绝符号链接/目录联接。静态路径中的 `data`、`logs` 等私有目录名会被预览器拦截，浏览器可公开的 JSON 等资源建议放 `assets/`。

本地可直接挂载原项目的发布目录。正式打包前由门户执行 `npm run prepare:apps -- capacity`，收集原样发布文件到忽略的 `apps/capacity/`，再按部署清单打包；源码仍由原项目维护。接入方会保留旧产物备份，不从收集目录反向修改业务。

**SPA 注意：当前静态预览不会自动将 `/capacity/某路由` 回退到 index.html。** 可在原项目采用支持的 hash 路由，或与门户方明确补充仅作用于该应用的 history 回退；不能用全站回退掩盖资源 404。

## 6. 独立后端交付要求

服务应能在指定目录下以前台命令启动，监听明确、可配置的回环地址和端口；不自行退出启动器后留下无法管理的后台进程，不自动占用门户或其他应用的端口。依赖和初始化命令需可在新 Windows 电脑重建。

公共前缀与后端内部路由可采用以下任一种策略，但浏览器获得的地址始终带应用前缀：

| 浏览器请求 | 保留前缀，stripPrefix=false | 剥离前缀，stripPrefix=true |
|---|---|---|
| `/capacity/api/state` | 后端收到 `/capacity/api/state` | 后端收到 `/api/state` |

即使后端剥离前缀，页面输出的 URL、Location、Cookie Path 等仍需遵循公共 `/capacity/`。门户不会改写这些响应内容。接入方会说明代理保留的公共 Host 和 Origin；新应用应通过自己的配置接受正确公共站点，而不是仅接受后端端口或关闭来源校验。

给接入方的配置示例（假设**原项目已实现**这些参数）：

```json
{
  "applications": {
    "capacity": {
      "type": "proxy",
      "target": "http://127.0.0.1:8891",
      "stripPrefix": true,
      "rootRoutes": [],
      "healthPath": "/api/health",
      "healthKeys": ["app_id", "status"],
      "start": {
        "cwd": "../产能分析",
        "command": "../.venv/Scripts/python.exe",
        "args": ["-B", "server.py", "--host", "127.0.0.1", "--port", "8891", "--public-base", "/capacity/"]
      }
    }
  }
}
```

这不是门户为业务项目提供的 CLI；如果你们没有这些参数，应在自己的项目中实现并验证，或交付现有等效接口。修改 target 不会自动改变服务的监听端口。上述端口只是可配置示例。

当前接入实现还需要满足以下具体约定：

- `target` 仅接受 `http://127.0.0.1:<port>`，不得带路径、查询、凭据；`localhost`、远程 HTTPS 和任意外网代理不在当前通用配置能力内。
- `start.cwd`、`start.command` 相对门户根目录解析；command 是可执行文件路径，不是 PATH 中的 `python`/`node` 名称，也不是包含参数的一整段命令。参数逐项写入 args；其中相对参数由业务服务按其 cwd/自身规则解析。若不能直接以前台可执行命令启动，可设 start=null，交付自行管理的独立服务。
- 通用 start 配置目前没有逐应用环境变量对象；公共前缀等优先使用原项目已有 CLI/配置。确需专属环境变量时与接入方明确其提供方式，不把机密塞进前端或注册表。
- 健康检查直接访问后端，不通过公共前缀；healthPath 支持 `/` 或 `/api/<单段小写名称>`，例如 `/api/health`。使用保留前缀方案时，也需提供可直连的检查地址。rootRoutes 仍只接受逐项登记的根 API，不因健康路径放开而扩大。
- 优先使用轻量 JSON 健康接口，返回 200 和简短 JSON，例如 `{"app_id":"capacity","status":"ok"}`；healthKeys 中的字段必须存在，启动器不验证 status 的值，未就绪时应返回非 2xx。已有项目没有独立健康接口时，可用 `healthKeys: []` 配合非空 healthText 检查固定页面标记；两种模式选择一种。超时 healthTimeoutMs 可设1000–10000毫秒，旧配置默认1500。探针不应执行完整导入或等待业务扫描锁，也不触发数据修改或跳转登录。数据速查现用首页标题标记及5000毫秒超时；存活检查不代表业务 API 已正常。
- 新应用 rootRoutes 应为空，公共 API 走应用前缀。遗留根 API 需要逐项评估冲突，不能占用门户管理地址 `/api/portal/health`、`/api/portal/stop`，不得复用 SOP 的身份头或密钥。
- 保留原应用的身份/来源校验。部门内部正常成员使用相同业务能力，接入不要求另建只读/可写角色；已有权限差异需要单独说明，不能由门户任务擅改业务权限。
- 上传、导出需说明请求格式、大小限制、文件名及冲突行为；代理会流式转发、保留 Content-Length；门户没有统一的上传大小/文件内容校验，业务服务需自行限制和校验。当前通用代理的无活动超时为 120 秒，并非长任务完成时限保证；长计算推荐业务服务返回任务标识后查询结果。
- **当前通用 Node 代理不支持 WebSocket upgrade。** 依赖 WebSocket、特定流式连接或特殊代理协议的应用，需接入方专项实现和验收；不能仅首页 200 就宣布可用。

可选 diagnosticChecks 仅供 `npm run diagnose` 逐项检查业务 API，例如 `[{"name":"目录接口","path":"/api/catalog","keys":["tables","status"]}]`；每项使用后端直连 API 和 JSON 顶层键，最多5项，不参与进程启动判定。这样目录扫描的慢响应或400不会被当作服务未启动，同时仍能单独报告业务故障。

服务日志由门户写入被忽略的独立文件，避免控制台文本选择暂停业务响应。门户只停止由它创建的进程树；已经独立运行并被复用的服务仍由原项目管理。门户不自动安装依赖，也没有通用的服务崩溃自动重启机制；上线需要另备常驻服务方案。门户页面另有默认 20 秒加载超时，不能与代理空闲超时混为一谈。业务自身的持久数据、日志和恢复机制仍应明确。

当前 Windows 部署另提供 SOP 和数据速查的专用依赖、代理及后台任务脚本，步骤见[部署指南](deployment.md)；它们不从本地 Node 配置自动部署任意新后端。数据速查原仓库和 `output_file/`、`input_file/` 需独立交付，门户包只附工具与模板。其 IIS 兼容代理仅开放 `/quicklook/` 和既有 11 个精确根 API，保留 Host、Origin、响应正文及安全头；ARR 全局设置由管理员配置。现有原服务 POST 校验只接受 `http://` 加 Host，HTTPS 写入是原项目待解决的兼容阻塞，门户不得替换 Origin 或关闭校验。

## 7. UI 与独立运行的边界

子网页继续由自己的项目维护界面、导航、图标和业务流程，门户设计基准只约束门户外壳。子网页的导航和布局由各自项目决定。

开发者需保证页面能在 iframe 视口中正常布局、滚动、输入、弹窗和下载，不依赖访问父页面 DOM。同源 iframe 是显示与路由容器，不构成业务安全沙箱；应用仍应遵守各自数据访问边界。已有内嵌模式可以交付其公开配置；没有内嵌模式也不是必须新增，只要实际页面能正常嵌入。页面切换会移除 iframe，未保存的输入和执行中操作应由子应用明确处理。

可选的后续能力包括自有内嵌模式、进度通知、外部身份对接等；目前门户没有通用 postMessage 业务协议或自动 SSO，不需要虚构这些接口。需要时先共同定义契约，再由各自项目实现。

## 11. 门户接入方的操作步骤

先读第 1–9 节契约；配置示例集中在第 5、6 节，不在此重复另一份。

1. **核对原项目**：定位门户根目录及原项目相对位置，读取项目说明，核对 Git 状态、版本、现有启动/构建参数和真实数据位置。记录业务冲突，不覆盖他人未完成工作；无法访问原项目的 AI 不能声称已经完成接入。
2. **确认类型和能力**：判断静态发布物或独立服务，检查子路径、iframe、API、数据持久化及健康检查。新能力缺失时按前述边界处理，不能复制第二套源码。
3. **配置实际挂载**：把第 5/6 节对应条目合并到 `integration/apps.json` 的 applications；本机差异放忽略的 `config.local/apps.json`。root/cwd/command 的相对值以门户根目录解析；按应用合并字段，start 是完整对象。SOP 沿用其专属 `config.local/sop.json` 与原网关，不套用通用代理的身份参数。
4. **登记入口**：按下一节更新 `portal/config/apps.json`，优先使用已有分组，已有 pending 项更新原条目。左侧导航和首页由配置生成，不手写重复标签。
5. **静态发布与打包**：本地可直接挂原项目发布目录；交付时由 `prepare:apps` 收集原样产物，并在部署配置的 `StaticApplications` 中登记相同 ID。`Import-OrderIQ.ps1` 只适用于 OrderIQ；其他应用使用通用收集或其已有产物交付方式。
6. **动态服务与本地运行**：`npm start` 启动 SOP 及配置中独立服务；`npm run dev:static` 只提供静态挂载/代理，不自动启动后端。先在同源 `/<id>/` 验证页面、接口和资源，再从 `/#/app/<id>` 验证门户内打开。新动态应用不由静态打包器自动收集完整服务；生产流程见[部署指南](deployment.md)。
7. **验收后开放**：完成第 9 节及第 13 节门户验证后设为 ready；本地验证不等于内网已上线。失败时保持 pending，交付实际阻塞及可恢复配置。
8. **业务后续更新**：原项目修改、验证后生成新发布物或更新独立服务；门户只更新必要接入。代码或运行配置变化后，用停止入口完整重启门户；启动器不会把不同数据目录或测试模式静默当作同一实例复用。

当前默认实例：SOP 原项目 `../SOP维护`，销量预测从 `../销量预测/output_file` 挂载，数据速查从 `../数据速查` 启动；具体数据、例外根 API 及本机配置见[使用指南](usage.md)。库存分析已移除，线索分析仍为 pending。源码位置不同先查明再配置，不以示例为理由搬动或复制项目。

## 12. 登记入口、排序与状态

以下是应用对象示例，合并进目标分组的 apps 数组；它不是完整注册表，不能直接覆盖整个文件。

```json
{
  "id": "capacity",
  "name": "产能分析",
  "subtitle": "Capacity",
  "description": "查看产能安排，辅助制定未来入库计划。",
  "url": "/capacity/",
  "icon": "chart",
  "enabled": true,
  "status": "pending",
  "order": 35,
  "version": null,
  "dataUpdatedAt": null
}
```

| 字段 | 含义 |
|---|---|
| id / url | 唯一 ID 与同源公共前缀；与挂载、代理、静态部署 ID 保持一致 |
| enabled | 导航/首页是否显示，不代表服务开关或访问权限 |
| status | pending 待接入、ready 已接入、maintenance 维护中；pending、maintenance 状态不会请求业务页面。ready 不是实时健康统计 |
| order | 数值越小越靠前；当前 SOP=10、订单=20、预测=30、线索=40、速查=50。新增项默认安排在数据速查之前，保持速查最后 |
| icon | 现有 chart、box、calendar、trend、users、grid、search 等线性图标；未知名称回退 grid |
| version / dataUpdatedAt | 可保存元数据；当前门户不展示版本/更新时间页脚 |

分组对象形如 `{"id":"supply","name":"供给协同","apps":[]}`，ID 也应唯一。`platform.defaultApp` 只能是 home 或已启用的 ready 应用。加载超时 loadTimeoutMs 默认 20000，允许 1000–120000 毫秒。

门户外壳遵循[统一设计规范](../design-system/planning-portal/MASTER.md)：灰蓝白底、紧凑左侧图标栏、不加重复标题和正常态操作条/页脚，不编造 KPI。该规范不要求子页面统一改版。

## 13. 门户验证与交付

从门户根目录执行：

```powershell
npm run check
npm test
```

check 会验证配置、JavaScript 语法和已接入静态入口；不启动动态业务服务，也不能证明接口、导入导出或 IIS 已正常。纯文档改动不需要启动业务后端；挂载/代理变化则应有针对路由、故障和隔离边界的验证。

除第 9 节联合验收外，门户方需验证导航高亮、直接业务地址、切换与前进后退、搜索/分组/无结果、pending/maintenance、404/服务停止/加载超时及失败重试；正常态无额外工具栏。检查桌面和手机、键盘焦点及实际截图，确认未改动子应用受控文件。

交付说明至少包括门户改动、原项目/发布物来源版本、数据位置、启动方法、已验证范围、未完成的服务器步骤和回退办法。必要检查通过后，审阅并仅暂存本次门户文件，默认提交推送当前分支上游，不强制推送；报告短提交号及结果。受阻时保留提交、说明原因，不把本地验收说成生产部署。
