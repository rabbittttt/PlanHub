# 子网页开发者接入规范

适用对象：为“智选车计划部数据平台”开发、维护独立业务网页的开发者及其 AI。核对日期：2026-11-04。

**你们继续在自己的项目中开发和发布，门户只提供统一入口、静态挂载或独立服务代理。接入不会自动修改业务 UI、算法、数据口径或权限。日常维护结果必须持久保存，服务或门户重启后继续使用。**

## 1. 最先确认的六条规则

1. **源码独立**：保留自己的项目、仓库、依赖、测试及启动方式；交付发布物或独立服务，不将整套业务源码放进门户维护。
2. **应用路径独立**：与接入方确定唯一 ID 和公共前缀，例如 `capacity`、`/capacity/`；浏览器页面、资源、接口、跳转和下载均留在该前缀内。
3. **允许同源嵌入**：页面可以直接访问，也能在门户同源 iframe 中使用；不依赖门户修改页面正文或操作 iframe 内的 DOM。
4. **可以迁移**：磁盘路径从项目位置或显式配置解析；域名、服务端口、数据位置可配置，不能依赖开发者电脑的盘符、用户名或临时目录。
5. **数据持久保存**：原项目或明确的数据目录负责数据库、维护表、上传及配置；门户不为日常操作建立每次启动即更换的业务副本。
6. **提供可验收交付**：说明启动/构建方法、数据路径、前缀策略和所需能力，并提供测试数据，完成页面和关键业务操作的验收。

## 2. 选用哪种接入方式

| 项目类型 | 开发者交付什么 | 门户如何消费 |
|---|---|---|
| 单文件 HTML 报表 | 原项目生成的 HTML、生成命令和来源版本 | 挂载原 HTML，或收集到忽略的发布目录 |
| 多文件静态网页 | 完整发布目录，包括 HTML、JS、CSS、字体、图片等 | 只挂载声明可公开的发布文件 |
| 带 Python / Node 等后端的应用 | 独立服务、依赖清单、启动参数、健康检查与数据位置 | 运行或复用服务，通过同源前缀代理访问 |

若页面需要 API、数据库或上传功能，不能仅交付前端文件就声称应用已完整接入。静态报表中已嵌入的数据也属于公开给访问者的页面内容，不能把真实报表上传到公开 Git 仓库。

## 3. 浏览器地址与资源、接口规则

### 3.1 三种路径要区分

以下文件系统路径以**门户根目录**为基准；你们项目自身配置中的相对路径应明确以**自己的项目根目录**为基准。

| 用途 | 示例 |
|---|---|
| 独立项目磁盘位置 | `../产能分析/` |
| 浏览器业务公共地址 | `/capacity/` |
| 门户导航地址 | `/#/app/capacity` |

门户导航地址不是业务页面地址。不要将 `file:///...`、后端的 `http://127.0.0.1:某端口/` 或某台电脑的 IP 写进页面作为业务入口。

应用 ID 使用小写字母开头，只含小写字母、数字和连字符；新应用统一约定 `/<id>/`，保留末尾斜线。IIS 静态应用名最长 40 个字符。避开 `home`、`sop`、`api`、`assets`、`css`、`js`、`config`、`data`、`logs`、`services`、`scripts`、`deploy`、`tests` 等已有或保留名称；分组 ID 的 `all` 也保留。先与接入方核对，不重复注册已有应用。

### 3.2 子路径必须贯穿整个页面

推荐资源地址为 `./assets/app.js` 或带正确公共前缀的 `/capacity/assets/app.js`；API 访问 `/capacity/api/...`。以下内容均需核对：

- CSS、JS、字体、图片、favicon、懒加载资源及动态 import。
- fetch/XHR、表单提交、文件上传、导出下载和打印资源。
- 登录返回、HTTP Location、页面内部链接、Cookie Path 及服务工作线程作用域（若使用）。
- SPA 的路由 base、刷新深层路由和直接打开书签地址。

不要让各应用争用站点根部的 `/api/`、`/assets/`、`/static/` 或 `/login/`。数据速查已有精确根 API 转发，是保留原实现的兼容方案，不是新应用的默认开发方式；同名根接口冲突不会靠 Referer 猜测分流。

如果需要同时保留独立运行与门户运行，使用原项目自己的构建或运行配置来选择公共前缀。例如由原项目生成不同的 `app-base` 元数据，前端按它构造地址：

```html
<!-- 门户模式；独立根路径运行时由原项目输出 content="/" -->
<meta name="app-base" content="/capacity/">
```

```js
const appBase = new URL(
  document.querySelector('meta[name="app-base"]').content,
  location.origin
);
const response = await fetch(new URL('api/state', appBase));
```

这是可采用的实现示例，不是门户自动注入的配置。仅将资源写成相对路径并不能解决 SPA 深层路由的基准问题，需要在自己的构建、路由和服务中一起核对。

### 3.3 允许同源 iframe

公共页面与门户需使用相同协议、主机和端口。最终 HTML 响应不得包含禁止嵌入的策略；通常可使用以下 HTTP 响应头：

```http
X-Frame-Options: SAMEORIGIN
Content-Security-Policy: frame-ancestors 'self'
```

与应用已有 CSP 合并，不要用这两行覆盖其余安全策略；`frame-ancestors` 应由 HTTP 响应头下发，不能依赖 HTML meta。不要在页面中强制 `top.location` 跳出门户。门户不会剥除子应用的响应安全头。

建议实现正确的 HEAD 响应。门户先 HEAD 探测页面，再 GET 加载 iframe；HEAD 不支持时应明确返回 405/501，不能无限等待、返回伪 200 错误页或重定向到前缀外。

## 4. 文件与数据路径：换电脑仍能运行

建议保持类似布局；文件夹名称仅为示例，不要求迁移现有项目来凑目录：

```text
工作区/
  计划工作台/       # 门户
  产能分析/         # 你们自己的源码、发布物及私有数据
  共享数据/         # 已明确归属的共用输入
  .venv/            # 若使用工作区共享 Python；换电脑重新创建
```

- 以脚本/项目位置解析默认路径，不能依赖“必须先 cd 到某目录”。命令行覆盖值和配置文件相对值的解析基准应写入项目说明。
- 分开代码、公开发布目录和持久数据目录；数据库、原始 Excel、日志、机密及临时上传不得落入可下载的静态目录。
- 页面读取服务器文件应通过业务 API；浏览器不能直接访问服务器磁盘路径。
- 共用 Excel 时声明谁负责写入、谁只读以及更新触发方式，不要求为接入合并各项目数据库或计算口径。门户目前不是自动“上传一次供全部应用导入”的数据中心。
- 保存计划、修改设置及导入数据应写入明确的持久目录。启动、重启或升级不能重新用默认种子覆盖已维护数据；演示/测试模式需显式选择。
- 说明服务停止、门户切换页面、浏览器关闭、重复请求、并发修改及 Excel 占用时的保存行为。重要维护数据不能只放内存或未持久化的前端状态。
- `localStorage`、IndexedDB、CacheStorage、Cookie 应使用应用专属名称，例如 `capacity:views:v1`，避免同源应用互相覆盖。Cookie Path 与 Service Worker scope（若使用）也应限制在应用前缀，不接管门户或其他应用。浏览器收藏/草稿属于浏览器存储；切换独立地址到门户地址或换电脑，不会自动迁移。需要部门共享的数据应在业务服务端保存。
- 业务数据、密钥、日志和真实报表不提交公开 Git；备份、恢复和数据迁移方式由原项目说明。不要复制旧电脑的 Python 虚拟环境到新电脑。

## 5. 静态网页交付要求

发布目录只包含浏览器使用的文件，保留资源目录关系。给出入口文件、公开文件清单和可重复执行的构建命令；交付来源版本或文件哈希，不让接入方猜哪个 HTML 是最新版。

下面是给门户接入方的配置示例，需**合并到现有 applications 中**，不能覆盖门户已有应用：

```json
{
  "applications": {
    "capacity": {
      "type": "static",
      "root": "../产能分析/dist",
      "entry": "index.html",
      "publicPaths": ["index.html", "assets/"]
    }
  }
}
```

`root` 相对门户根目录；`entry` 和 `publicPaths` 相对发布目录，使用 `/` 分隔、不含 `..`。公开子目录以 `/` 结尾，不使用 `*` 通配。前缀内的文件也必须在公开清单和 MIME 白名单内才可访问。

当前静态预览与收集工具支持 `.html .css .js .mjs .json .svg .png .jpg .jpeg .gif .webp .ico .woff .woff2 .txt`。PDF、CSV、WASM 等尚需门户另行补充并验证支持；不要假定所有扩展名都会被提供。发布物使用真实文件，收集工具拒绝符号链接/目录联接。静态路径中的 `data`、`logs` 等私有目录名会被预览器拦截，浏览器可公开的 JSON 等资源建议放 `assets/`。

本地可直接挂载原项目的发布目录。正式打包前由门户执行 `npm run prepare:apps -- capacity`，收集原样发布文件到忽略的 `apps/capacity/`，再按部署清单打包；源码仍由原项目维护。接入方会保留旧产物备份，不从收集目录反向修改业务。

**SPA 注意：当前静态预览不会自动将 `/capacity/某路由` 回退到 index.html。** 可在原项目采用支持的 hash 路由，或与门户方明确补充仅作用于该应用的 history 回退；不能用全站回退掩盖资源 404。

## 6. 独立后端交付要求

服务应能在指定目录下以前台命令启动，监听明确、可配置的回环地址和端口；不自行退出启动器后留下无法管理的后台进程，不自动占用门户或其他应用的端口。依赖和初始化命令需可在新 Windows 电脑重建。

公共前缀与后端内部路由可采用以下任一种策略，但浏览器获得的地址始终带应用前缀：

| 浏览器请求 | 保留前缀，stripPrefix=false | 剥离前缀，stripPrefix=true |
|---|---|---|
| `/capacity/api/state` | 后端收到 `/capacity/api/state` | 后端收到 `/api/state` |

即使后端剥离前缀，页面输出的 URL、Location、Cookie Path 等仍需遵循公共 `/capacity/`。门户不会改写这些响应内容。接入方会说明代理保留的公共 Host 和 Origin；新应用应通过自己的配置接受正确公共站点，而不是仅接受后端端口或关闭来源校验。

给接入方的配置示例（假设**原项目已实现**这些参数）：

```json
{
  "applications": {
    "capacity": {
      "type": "proxy",
      "target": "http://127.0.0.1:8891",
      "stripPrefix": true,
      "rootRoutes": [],
      "healthPath": "/api/health",
      "healthKeys": ["app_id", "status"],
      "start": {
        "cwd": "../产能分析",
        "command": "../.venv/Scripts/python.exe",
        "args": ["-B", "server.py", "--host", "127.0.0.1", "--port", "8891", "--public-base", "/capacity/"]
      }
    }
  }
}
```

这不是门户为业务项目提供的 CLI；如果你们没有这些参数，应在自己的项目中实现并验证，或交付现有等效接口。修改 target 不会自动改变服务的监听端口。上述端口只是可配置示例。

当前接入实现还需要满足以下具体约定：

- `target` 仅接受 `http://127.0.0.1:<port>`，不得带路径、查询、凭据；`localhost`、远程 HTTPS 和任意外网代理不在当前通用配置能力内。
- `start.cwd`、`start.command` 相对门户根目录解析；command 是可执行文件路径，不是 PATH 中的 `python`/`node` 名称，也不是包含参数的一整段命令。参数逐项写入 args；其中相对参数由业务服务按其 cwd/自身规则解析。若不能直接以前台可执行命令启动，可设 start=null，交付自行管理的独立服务。
- 通用 start 配置目前没有逐应用环境变量对象；公共前缀等优先使用原项目已有 CLI/配置。确需专属环境变量时与接入方明确其提供方式，不把机密塞进前端或注册表。
- 健康检查直接访问后端，不通过公共前缀；当前 healthPath 格式仅支持 `/api/<单段小写名称>`，例如 `/api/health`。使用保留前缀方案时，也需提供这个后端直连检查地址，或由门户另行扩展并测试。
- 健康检查返回 200 和简短 JSON，例如 `{"app_id":"capacity","status":"ok"}`；healthKeys 中的字段必须存在。当前启动器只核对 HTTP 成功和键是否存在，**不会验证 status 的值**；未就绪时应返回非 2xx。检查应尽量在 1.5 秒内完成，不跑完整导入、不触发数据修改、不要求跳转登录。
- 新应用 rootRoutes 应为空，公共 API 走应用前缀。遗留根 API 需要逐项评估冲突，不能占用门户管理地址 `/api/portal/health`、`/api/portal/stop`，不得复用 SOP 的身份头或密钥。
- 保留原应用的身份/来源校验。部门内部正常成员使用相同业务能力，接入不要求另建只读/可写角色；已有权限差异需要单独说明，不能由门户任务擅改业务权限。
- 上传、导出需说明请求格式、大小限制、文件名及冲突行为；代理会流式转发、保留 Content-Length；门户没有统一的上传大小/文件内容校验，业务服务需自行限制和校验。当前通用代理的无活动超时为 120 秒，并非长任务完成时限保证；长计算推荐业务服务返回任务标识后查询结果。
- **当前通用 Node 代理不支持 WebSocket upgrade。** 依赖 WebSocket、特定流式连接或特殊代理协议的应用，需接入方专项实现和验收；不能仅首页 200 就宣布可用。

服务日志由门户写入被忽略的独立文件，避免控制台文本选择暂停业务响应。门户只停止由它创建的进程树；已经独立运行并被复用的服务仍由原项目管理。门户不自动安装依赖，也没有通用的服务崩溃自动重启机制；上线需要另备常驻服务方案。门户页面另有默认 20 秒加载超时，不能与代理空闲超时混为一谈。业务自身的持久数据、日志和恢复机制仍应明确。

## 7. UI 与独立运行的边界

子网页继续由自己的项目维护界面、导航、图标和业务流程，门户设计基准只约束门户外壳。接入不要求复制门户顶栏、删除子网页原有侧栏或为了“统一主题”重做 UI。

开发者需保证页面能在 iframe 视口中正常布局、滚动、输入、弹窗和下载，不依赖访问父页面 DOM。同源 iframe 是显示与路由容器，不构成业务安全沙箱；应用仍应遵守各自数据访问边界。已有内嵌模式可以交付其公开配置；没有内嵌模式也不是必须新增，只要实际页面能正常嵌入。页面切换会移除 iframe，未保存的输入和执行中操作应由子应用明确处理。

可选的后续能力包括自有内嵌模式、进度通知、外部身份对接等；目前门户没有通用 postMessage 业务协议或自动 SSO，不需要虚构这些接口。需要时先共同定义契约，再由各自项目实现。

将以下内容放入你们项目的 README 或独立接入说明，并交给门户接入方：

| 项目 | 需要填写 |
|---|---|
| 应用身份 | 中文名称、唯一 ID、用途、负责人、项目/仓库位置 |
| 版本 | 源提交或发布版本；工作区是否有未提交修改 |

| 启动/构建 | 解释器或运行时版本、依赖安装、完整命令及执行目录 |
| 页面/资源 | 静态入口、发布目录、资源文件清单、所需扩展名、SPA 路由模式 |
| 服务 | 监听地址/端口、前缀保留或剥离、启动参数、健康检查及返回样例 |
| 数据 | 输入、数据库、维护表、上传、导出、配置的相对路径和解析基准 |
| 持久与共享 | 重启保存行为、共用输入的写入归属、浏览器存储是否需要迁移 |

| 运维 | 停止/重启、日志、备份/恢复、升级/回退、生产运行所需条件 |

门户方另行维护导航的分组、排序、状态，以及挂载/代理/打包配置。应用入口登记完成不等于页面已发布，页面能打开也不等于业务功能验收完成。

## 9. 联合验收清单

- [ ] 原项目可独立运行；迁移父目录或从其他 cwd 启动后，配置路径仍正确。
- [ ] 从业务公共地址和门户 iframe 打开均正常；刷新、内部导航、深层路由及返回工作台正常。
- [ ] 无资源/API 404、前缀外跳转或端口写死；离线/内网必需资源完整，外部依赖已明确。
- [ ] 使用测试数据验证查询、保存、导入导出、下载及必要的身份/来源校验；不向正式计划写入验收数字。
- [ ] 保存后停止并重新启动，接口仍读回相同数据；升级不会默认清空或重新种入旧数据。
- [ ] 同名文件、Excel 占用、并发修改、失败重试等有可理解的结果，不静默覆盖。
- [ ] 门户切换导致 iframe 关闭时，未保存内容、浏览器草稿和后台任务的行为已核对。
- [ ] 桌面和窄屏正常，筛选/输入/弹窗可用；应用无控制台异常。
- [ ] 服务停止、端口占用、健康检查失败时提示明确；静态目录无法下载数据库、原始输入或机密。
- [ ] 交付说明、样例、依赖、源码版本、发布物及回退方法齐全。

验收通过后由门户方将注册状态设为 ready。本地 Node 接入配置不会自动生成完整 IIS 代理/常驻服务；部署到部门 Windows 台式机的服务、端口和运维步骤需另行准备和验收。

## 10. 可直接发给开发者 AI 的简短任务
