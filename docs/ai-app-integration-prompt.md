# 可直接转给其他 AI 的接入任务

将下面整段复制给负责接入的 AI，填写已知信息，并让它能访问门户和业务原项目。没有文件访问权限的 AI 只能提供方案，不能声称已完成接入。

字段不确定时写“待核实”；AI 应先查看项目中已有信息，再集中指出真正缺少的内容。完整步骤见[新业务页面接入指南](app-integration.md)。

## 复制以下任务

```text
请将下面的业务页面接入“智选车计划部数据平台”，仅完成门户侧集成和本地验收，不重新设计门户架构。

【不可越界】
- 门户只做集成，不修改子应用源码、UI、文案、图标、业务逻辑、权限实现、数据规则、测试或发布产物内容。
- 不通过 iframe DOM、CSS/JavaScript 注入、裁剪内容或代理正文替换来间接修改子页面。
- 仅使用子应用已有的启动/构建/接入配置接口。必须修改子应用才可接入时，列出具体问题、文件与影响，留待另行明确授权的子应用任务；不要直接修。
- 已有子应用改动保留，不在本任务回退。默认提交推送不授予对子应用仓库写入或推送的权限。

【本次应用】
- 中文名称 / 业务用途：
- 门户项目根目录：.（先定位包含 package.json、portal/、deploy/ 的目录，以下路径相对此目录）
- 业务原项目相对路径 / 仓库：例如 ../业务项目/，先核实实际位置
- 应用 ID / 公共子路径：例如 capacity / /capacity/
- 门户分组：现有分组优先；若是已有 pending 应用，请更新原条目
- 类型：单 HTML / 多文件静态站点 / 动态服务 / 待核实
- 原项目启动或构建命令：
- 静态发布目录，或后端回环端口：
- 数据、规则、上传、导出目录：填写相对路径，并标明解析基准
- 使用范围：部门内部，所有已获准访问的成员拥有相同业务功能，不区分只读/可写角色
- 其他限制与验收数据：

【先阅读并检查】
1. 读取门户根目录 AGENTS.md、design-system/planning-portal/MASTER.md、docs/app-integration.md 及对应参考图；读取业务原项目的协作说明。
2. 核对两个项目的真实路径、Git 状态、源码版本、构建和运行方式，检查现有注册表、本地映射、打包清单与部署逻辑。
3. 根据项目证据确定接入类型，列出具体修改步骤后开始。若有无法判断的业务冲突、部门访问边界或缺失路径，明确指出，不覆盖现有工作；可独立完成的部分继续推进。

【路径约定】
- 文档、命令及本地模板使用相对路径，不写死盘符、用户名或某台机器的工作区目录。
- 先确认门户根目录与原项目的相对位置；本任务命令从门户根目录运行。
- config.local/sop.json 的相对路径按门户根目录解析，不按 config.local 文件夹解析；其他工具按各自现有规则核对。
- 构建器或服务器接口要求绝对路径时，由当前环境动态解析生成，不修改校验来强塞相对路径。

【源码与数据归属】
- 业务源码和数据仍归业务原项目，本任务只读核对，不合入任何补丁。使用已有子路径、内嵌与身份接口，不改其独立运行行为。
- 门户只保存接入配置及通用预览/部署逻辑。静态发布物可导入忽略的 apps/<id>/，不能作为第二套可维护业务源码。
- 不把原始 Excel、数据库、日志、密钥或整个业务项目复制进静态目录或提交公开仓库。
- SOP 唯一源码默认在 ../SOP看板（相对门户根；布局不同时先查明再配置）；不得恢复门户 services/sop 源码副本。
- 现有文件和数据先核对再改，必要时保留可恢复备份，不删除业务数据或已有恢复备份。

【接入约束】
- apps.json 仅登记入口，不会自动发布页面、启动服务或建立代理。
- 门户 URL 必须为同源根相对子路径 /<id>/，带末尾斜线；不把本地后端端口或外域 URL 填入注册表。
- 静态应用核对 portal/config/apps.json、scripts/dev-server.mjs 的 STATIC_APPS、实际产物 apps/<id>/、部署 JSON 的 StaticApplications 四处是否一致。
- 动态应用明确保留/剥离前缀策略，并检查资源、API、跳转、Cookie Path、上传下载和 WebSocket。
- 当前 npm start/dev 只自动启动独立 SOP；其他后端需要自己的受控同源预览与部署支持。不能放宽同源校验或关闭安全策略来绕过缺少的接入逻辑。
- 核对页面是否允许同源 iframe；直接访问业务地址和 iframe 内访问都要正常。不支持时报告阻塞，不修改子应用或剥除响应头。HEAD/iframe 成功不代表业务 API 或权限已验收。
- 部门成员统一使用查看、维护、导入导出等已有业务功能；门户不新增角色、写入域组或逐用户授权，也不修改子应用已有权限规则。保留部门访问边界、可信操作人记录及 Origin/代理校验；不能用隐藏菜单代替访问控制。
- 全局维护暂停写入与成员角色是两回事。现有 SOP 预览写入隔离快照，不回写原项目；重启会创建新快照。
- 新增入口先 pending；本地临时 ready 验收后，如有未完成内容需恢复 pending 或明确交付范围，不能把尚未完成的接入宣布为已上线。

【界面约束：仅适用于门户外壳，不约束子应用】
- 沿用白底灰蓝、细边框、浅灰导航选中块和蓝色开口 P 标识（直竖、深浅蓝层次及小浅蓝折面）；桌面品牌与应用标签为约 64px 单行顶栏，窄屏顶部展开。
- 不加侧边栏、重复应用标题、正常态应用操作条、版本/时间页脚或虚假 KPI。失败重试放在错误面板。
- 子应用的全部 UI 和行为保持原样，包括筛选、编辑、导入导出、页脚和提示栏；门户主题不得覆盖 iframe 内部样式。
- 界面设计使用可用的 ui-ux-pro-max 技能，并以项目现有设计基准为准。不要引入外网字体、CDN 依赖或无关框架。

【验收与交付】
- 运行 npm run check，以及与变更有关的现有检查；改挂载/代理时验证其路由、错误和隔离行为。
- 浏览器验证：独立地址、门户嵌入、刷新、前进后退、顶部切换、搜索、分组、无结果、待接入与失败重试。
- 用测试数据验证相关 API、导入、导出、下载、打印、存储；页面有这些功能才逐项验收，不写“看上去正常”。
- 检查桌面/手机、无横向溢出、键盘焦点和截图；明确部门访问边界、Windows 身份留痕与成员相同操作能力是否实际验证。
- 准备配置草案、发布物来源和回退说明，但不要自动部署、改仓库可见性、重写 Git 历史或修改 IIS/安全设置。
- 相关必要检查通过后，仅在门户仓库创建 Git 提交，并推送到当前分支已配置的上游，无需再次询问。仅提交本次任务相关文件，核对远程和分支，不强制推送；交付时报告短提交号和推送结果。若推送受阻，保留提交并说明具体原因。
- 最终说明：门户改了哪些文件、原项目是否保持未修改、数据放在哪里、如何启动、验证结果、未完成事项及需人工执行的服务器步骤。没有做过的验证要明确标注。
```

## 转交时建议一并提供

- 本次业务应用原项目的位置和访问方式，不只给一个网页截图。
- [接入指南](app-integration.md)、[设计基准](../design-system/planning-portal/MASTER.md)及其中的参考图；若 AI 能读取完整门户仓库，直接告知它先读根目录 AGENTS.md 即可找到入口。
- 可用于验收的测试文件或样例，以及允许修改的范围。真实机密通过合适的本地配置提供，不粘贴到公开文档中。

接入完成后，将实际应用 ID、源码归属、启动/构建命令、路径/代理约定、数据目录、验证和回退信息记入该应用自己的接入记录，并在后续更新时维护。
