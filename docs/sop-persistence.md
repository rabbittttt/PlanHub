# SOP 门户持久数据接入

2026-11-04 用户确认：门户是日常操作入口，维护必须保存到正式数据，重启不能换成新快照。此规则替代历史预览文档中的默认隔离约定；业务源码仍只在 SOP 原项目维护。

## 正常操作

双击“启动本地门户.cmd”，或运行 npm start / npm run dev / npm run dev:sop。三者默认直接使用原 SOP 的数据库、销售来源与计划维护表。门户只在 artifacts/sop-runtime-... 下生成接入配置，不复制业务数据；该目录不是数据库，重新生成配置不会清空维护结果。

默认相对门户根目录：

| 内容 | 路径 |
|---|---|
| 唯一业务源码 | ../SOP维护 |
| 数据库 | ../SOP维护/data/sop.sqlite3 |
| 销售数据与来源设置 | ../SOP维护/data/sales.json、source_settings.json |
| 原始订单 | ../共享数据/订单汇总 |
| Excel 计划维护表 | ../共享数据/SOP计划/SOP计划维护.xlsx |
| SOP 自带历史备份 | 原数据目录下的 backups |

配置沿用 config.local/sop.json 的 sourceRoot、dataRoot、sharedConfig；--data-root 为明确的持久数据项目。SOP_DATA_DIR 可直接指定数据目录，SOP_SOURCE_DIR 与 SOP_PLAN_DIR 可分别指定销售和计划目录。相对值均按门户根目录解析，换电脑不依赖本机盘符。默认布局迁移时应一起迁移原项目数据和共享目录，而不只是门户源码。

计划保存写入原 SQLite，已存在的 Excel 维护表按原应用机制同步。没有维护表时数据库仍可保存；是否创建 Excel 由原应用的“创建Excel（可选）”操作决定。门户不改变这项业务行为，也不强制解决 Excel 占用或版本冲突。

只保留一个写入同一数据库/维护表的 SOP 服务，日常由门户启动即可；不要另开原项目启动器重复写入。当前仍是本机入口，不代表部署到部门网络，未修改 IIS 或身份策略。

## 历史副本与测试

原有 artifacts/sop-preview-* 及其他恢复备份全部保留。切换时只读核对了 22 个历史预览数据库；唯一原库之外的审计事件来自明确标注“部门统一功能隔离验收”的演示数据，不合并到正式库。核对报告位于忽略的 artifacts/sop-persistence-audit.json。

显式 --snapshot 仅用于测试人员的副本验收；--seed-from 必须与 --snapshot 配合，旧测试命令不会静默转成正式写入。--snapshot --demo 使用演示数据。正常启动不需要也不应添加这些参数。

## 验证

使用原 SOP 服务和独立测试数据，通过门户保存计划 246，确认测试数据项目的 SQLite 与已有 Excel 维护表均包含该值；停止整个服务后重新启动，接口仍返回 246，运行目录仅有网关配置，没有创建业务快照。测试没有向正式计划写入测试数量。保留原有显式快照测试，验证两种模式不会混淆。

正式数据首次联调前已通过 SQLite backup API 备份原库，并保留销售数据、来源设置及计划表，位置为忽略的 artifacts/sop-before-persistence-usA4Bq。随后实际启动默认持久模式，页面、会话、状态接口均返回 200，网关指向原 data 目录及共享计划表，原应用报告维护表 synced；联调只发送读取请求。

旧文档中的迁移及隔离验收记录作为历史证据保留，不是当前默认运行方式。未来 AI 修改门户时必须延续默认持久化与各子项目独立维护原则。
